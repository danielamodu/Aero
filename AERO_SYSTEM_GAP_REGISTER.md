# Aero System Gap Register

Severity describes product/security readiness, based on repository evidence on 2026-10-21. “Critical” means a direct blocker to using the described system as a reliable consumer financial product. Repo line references are approximate evidence locations and should be rechecked when code changes.

| ID | Severity | Gap / defect and evidence | Consequence | Recommended remediation |
|---|---|---|---|---|
| G-01 | Critical | No consumer account/auth model. Wallet connection is UI-level (`components/testnet/shell.tsx:74`, `app/testnet/page.tsx`); app persistence is waitlist-only (`lib/db.ts`, `app/api/waitlist/route.ts`). | No stable user ID, recoverable account, linked-wallet ownership proof, or account-scoped financial authorization; connected wallet must not be represented as an authenticated Aero user. | Define stable user identity and verified wallet-link challenge/signature model, session lifecycle, recovery, revocation, multi-wallet policy, deletion, and server-side authorization before account features. |
| G-02 | Critical | No internal financial ledger or DB transaction state. Payments execute from the browser (`components/testnet/views.tsx:447-489`) and contract events are the durable evidence; there is no payment/transaction schema or migration. | The app cannot reliably reconstruct a canonical user financial history, coordinate retries, represent pending/reverted/reorged states, or reconcile a product ledger to chain state. | Add immutable transaction/payment records and an event journal with idempotency keys, chain/tx/log identity, explicit state transitions, safe retry, reorg handling, and reconciliation. |
| G-03 | Critical | “Bill payment” is a UI preset (`components/testnet/views.tsx:809`, `PayScreen`) that fills an ordinary transfer form; no provider API or bill entity exists. | Users may mistake a peer transfer to a demo recipient for settlement with a utility, landlord, or merchant. No provider confirmation, reversal, or dispute exists. | Keep the sandbox label explicit. For real billing, add provider abstraction, verified quotes/execution, callback authentication, fulfillment state, idempotency, reversal/dispute workflow, and linked financial records. |
| G-04 | Critical | Integrated yield deployments are mock based: `DeployMore.s.sol` creates `MockQiToken` markets and BenqiAdapter wrappers; `AeroVault.sol` describes synthetic rate/index accrual. | Yield balances/rates are simulations/subsidies, not real lending yield. Funding with real assets against the current mock stack would be unsafe and misleading. | Do not accept production funds in the mock configuration. Define protocol-supported deployment, adapter review, live fork tests, independent audit, and verified deployment/configuration acceptance before any real-value rollout. |
| G-05 | High | No repository-owned DB schema/migrations. `app/api/waitlist/route.ts` assumes a `waitlist` table; `lib/db.ts` only creates a client. | Constraints, unique email/referral behavior, referential integrity, upgrade path, and transaction isolation are unverified; future account/payment writes have no schema foundation. | Add versioned migrations and schema documentation. Establish unique constraints, foreign keys, indexes, isolation and retention policies; validate against a disposable test database. |
| G-06 | High | Activity history is incomplete and partly browser-local. `lib/onchain-activity.ts:52` queries a bounded block window and token/AeroVault events; `components/testnet/views.tsx:491-507` writes local activity. | History may disappear across devices, omit older/router events, or show optimistic local presentation without a canonical backend record. It is not a statement/reconciliation surface. | Build a reorg-aware event indexer or equivalent full history service and tie indexed chain events to account/wallet records. Clearly distinguish pending from finalized state. |
| G-07 | High | Withdrawal has no queue/reserve and is all-or-nothing (`contracts/src/AeroRouter.sol:249-276`, `_redeemProRata`). | An illiquid or reverting adapter can block a user's withdrawal even when other positions are liquid. No async claim or operational escape hatch exists. | Choose and document liquidity policy; add bounded reserve/queue/partial-exit behavior, pause/emergency controls, operator monitoring, and failure drills before real deposits. |
| G-08 | High | Admin sessions are deterministic HMACs of the shared password and have no server-side expiry/revocation (`lib/admin-auth.ts`; cookie maxAge in `app/api/admin/login/route.ts:21-28`). | A copied cookie remains valid until password rotation even after browser logout/expiry; no per-staff attribution or audit log exists. | Use managed identity or opaque random server-validated sessions with expiry/rotation/revocation, per-user roles, CSRF protections, and append-only admin action logs. |
| G-09 | High | Waitlist confirmation tokens use a code fallback when `WAITLIST_SECRET` is unset (`lib/waitlist.ts:3-10`). | If deployed without the secret, token generation is predictable from public email/username values; account confirmation could be forged. | Fail startup/route closed in production when the secret is absent; rotate to a high-entropy secret, use expiring single-use tokens, and avoid token material in logs. |
| G-10 | High | `npm audit --omit=dev` reported seven high severity advisories in transitive `braces`/`micromatch`/`fast-glob`/shadcn-related dependency paths. | Vulnerable dependency versions remain in the current lock graph. npm's suggested `--force` route is a breaking shadcn upgrade, so no safe direct fix was established by the audit. | Trace direct/indirect dependency paths, update within compatible ranges or pin overrides where supported, run audit and build/lint/typecheck in CI, and review the forced upgrade separately. |
| G-11 | High | No automated app tests or CI workflows were found; no build/typecheck/lint/test was executed for this audit. | Frontend flows, route behavior, generated ABI consistency, and integration regressions are not gated before deployment. | Add CI for lint/typecheck/build, contract tests, and browser tests covering auth gates, wallet network, payments, yield deployment gates, and mock/real labels. |
| G-12 | High | Router owner has no pause/timelock/multisig in source; owner can change allocation and adapter set (`contracts/src/AeroRouter.sol`); ownership and key control are unknown. | Admin key compromise or mistake can change strategy configuration; no delayed review, emergency circuit breaker, or known operational owner policy. | Define governance/key custody, multisig and timelock controls, pause semantics, emergency withdrawal boundaries, event monitoring, and incident procedures. |
| G-13 | High | Waitlist JSONL fallback is best effort and local (`app/api/waitlist/route.ts:23-34,126-129`; `lib/db.ts`). | Serverless instances may not share durable data; write errors are swallowed and API still reports success. Admin file operations can race. | Require durable shared storage in deployed environments; fail clearly on persistence failure; keep local fallback development-only. |
| G-14 | Medium | Signup email confirmation uses request-derived origin (`app/api/waitlist/route.ts:80-81`; `lib/waitlist.ts:12-14`). | A deployment/proxy that accepts an attacker-controlled Host/origin may send a valid confirmation token in a link on an attacker-controlled domain. | Build links from a configured canonical/allowlisted origin and test proxy host handling. |
| G-15 | Medium | Waitlist SQL duplicate lookup, insertion, position/referral reads, and email send are separate operations (`app/api/waitlist/route.ts:90-123`); table constraints are unknown. | Concurrent duplicate signups can race; confirmation/email state can diverge, and failed delivery has no job/retry record. | Add DB uniqueness and transactional upsert; persist outbox jobs and delivery status, then retry idempotently. |
| G-16 | Medium | In-memory rate limiter is per process and trusts forwarded IP headers (`lib/rate-limit.ts`). | Limits are bypassable across serverless instances/cold starts and may be ineffective if proxy headers are not sanitized. | Use a distributed limiter at the trusted edge/store and derive client IP only from trusted proxy configuration. |
| G-17 | Medium | AeroPay accepts an arbitrary token address and zero amount (checks recipient/memo only in `contracts/src/AeroPay.sol`); UI approves `maxUint256` (`components/testnet/views.tsx:451-456`). | Contract has broad token-call surface; allowance remains until revoked. This matters most if deployed beyond controlled testnet or if pay contract is replaced/compromised. | Restrict supported assets, reject zero amount, prefer exact or bounded approvals, and provide revoke/allowance visibility. Reassess before production. |
| G-18 | Medium | `DeployMore.s.sol` checks token code/decimals and deployed config/version but not `block.chainid` (`contracts/script/DeployMore.s.sol`). | An operator can accidentally broadcast the mock stack to a different chain if RPC selection is wrong; script broadcast is a sequence and may partially execute. | Assert Fuji chain ID (43113), preflight all config/owner/binding inputs, record deployment outputs in a manifest, and add post-deploy code/config verification before changing frontend env. |
| G-19 | Medium | Router's deployment gate verifies bytecode, version constant, asset, slot count, and adapter getter probes (`components/testnet/views.tsx:945-976`; router `configurationValid()`), not source provenance. | A wrong/malicious contract could mimic the expected interface and version; gate cannot establish audited bytecode or intended chain deployment. | Verify runtime bytecode against reproducible build/deployment manifest and allowlisted address+chain, and publish deployment provenance. |
| G-20 | Medium | Adapter withdraw path measures asset receipt, but doesn't explicitly assert adapter shares decreased by the requested amount (`contracts/src/AeroRouter.sol:298-315`). | A nonconforming owner-selected adapter could leave stale share accounting after sending assets, causing future valuation inconsistency. | Require share-balance delta/burn invariants and test malicious/non-burning withdrawal adapters before enabling arbitrary adapter additions. |
| G-21 | Medium | Activity code labels only vault deposit/withdraw plus token transfers and does not index router deposit/withdraw events as the principal yield history (`lib/onchain-activity.ts:51-93`). | Router position movements may not appear consistently in history/notices; app's yield digest and timeline can diverge from actual router records. | Index AeroRouter events and adapter/market accounting consistently; define one canonical source for balances and history. |
| G-22 | Medium | No support tickets, inbound email, delivery webhooks, case ownership, or disputes; only outbound waitlist email is implemented (`lib/waitlist-email.ts`, `app/api/admin/*`). | Consumer payment failures cannot be triaged with a durable case record or linked evidence. | Add support intake, user identity link, secure message storage, staff roles/notes, status/assignment, attachments, and dispute evidence once account foundations exist. |
| G-23 | Low | Public docs/marketing describe broader consumer features such as real bill pay, always-on yield, and automatic routing while source contains sandbox shortcuts (`app/docs/page.tsx`, `components/aero/landing.tsx`, `components/testnet/buy-sheet.tsx`, `AeroVault.sol`). | Product claims can exceed current implementation and confuse testnet visitors about real providers, yield sources, and funds. | Align copy and UI disclosures with implemented/testnet status; define claim review as part of release acceptance. |
| G-24 | Low | Router APY is an annualized rate aggregation, and the router uses static owner-set targets; no keeper/market optimizer exists (`AeroRouter.sol:128-166,345+`, `contracts/docs/AeroRouter.md`). | “Best yield” or “automatic optimizer” expectations are not met; a caller must trigger rebalance and targets are administrative. | Describe as target-weight routing with reported annualized rates unless/ until a strategy-selection and keeper system is built and monitored. |
| G-25 | Low | The B2.1.1 current router/adapter/frontend remediation is present in dirty local source but no current deployment evidence exists. | Source fixes may not be the bytecode at configured Fuji addresses; the UI gate mitigates some mismatches but doesn't certify addresses. | Treat remediation as not deployed until a controlled deployment, reproducible verification, address manifest, and post-deploy integration acceptance are recorded. |

## Priority interpretation

1. G-01/G-02/G-05 are foundational dependencies for a reliable financial product.
2. G-03/G-04/G-07/G-12 are hard blockers to describing billing/yield as production financial services.
3. G-08/G-09/G-10/G-11/G-13/G-18/G-19 are operational/security readiness work.
4. G-06/G-14/G-15/G-16/G-17/G-20/G-21/G-22/G-23/G-24/G-25 should be scheduled with the systems they depend on.
